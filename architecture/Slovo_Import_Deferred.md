# Slovo — Виробництво бібліотеки `library.db` (імпорт) — ВІДКЛАДЕНО, окремий проєкт

> **Статус: заморожено 2026-09-13 за рішенням Vitalii.** Виробництво **однієї бази `library.db`** на всю бібліотеку (R3-06; колишні `*.book`/`*.bible` скасовані) — розбір `books.chm`, нормалізація тексту, валідація готового файлу — окремий проєкт, який не входить в архітектуру застосунку. Цей файл — «парковка»: сюди перенесено все, що вже було напрацьовано в `Slovo_01/02` та аудитах, щоб не загубити. Основні документи описують лише **контракт формату бази** (`Slovo_02`, розділи «Схема `library.db`», «Власна `sqlite3.dll` зі Snowball», «Вимоги до файлу бази та параметри конекції», «Одиниця текстових офсетів») — це вхід для цього проєкту.
>
> **Оновлено 2026-10-30 (R6).** Форми слова в застосунку дає Snowball усередині SQLite (B-31): виробник будує, крім точних, **стемовані FTS-таблиці на кожну мову** тією самою власною `sqlite3.dll`, що й застосунок (§3, §4). Додано IMP-6.
>
> **Оновлено 2026-11-01 (R6).** Усі питання IMP-1…IMP-6 закрито (§5): нормалізація — мінімальна технічна; метадані — `books.csv` у репозиторії; детермінований порядок + текстовий дамп; корпус книг — російською; тести — дамп + критичні фрагменти; колонки `Abbreviation` уже у форматі; епіграф — один блок.

## 1. Що вже відомо про корпус (реверс-інжиніринг CHM)

- 962 HTML-файли, 39 книг EGW (`MB`, `GC`, `DA`, `SC`, `T1`–`T9`, `SM1`–`SM3` …) + категорії `history`/`spiritual`/`prophecy` з тією самою розміткою `glava`/`glava2`/`glink`, але без маркерів сторінок.
- Маркери сторінок `[N]` — оригінальні англійські номери сторінок; завжди в ізольованому `<p>`, ніколи посеред абзацу; логічний абзац може перетинати межу сторінки.
- `class="glava"` / `class="glava2"` — межі глав; `class="glink"` — внутрішня навігація, викидається.
- `utr_chtenia` («Утренние чтения») — інша структура (365 записів, `b_glava`/`glink3`), поза MVP.
- Біблійні перехресні посилання в тексті — звичайний текст; клікабельність — рантайм-фіча UI, не імпорту.

## 2. Правила розбору HTML → Domain (перенесено з `Slovo_01`)

| Сирий HTML-патерн | `TParagraphKind` | Структурний ефект |
|---|---|---|
| `<p class="glava">` | `pkChapterTitle` | Починає НОВУ `TChapterContent` |
| `<p class="glava2">` | `pkSubChapterTitle` | Теж починає НОВУ `TChapterContent` (у файлах-компіляціях) — структурно рівнозначний `glava`, різниця лише в Kind для стилізації |
| `<p><i>...</i></p>` одразу після `pkChapterTitle`/`pkSubChapterTitle` | `pkEpigraph` | Не впливає на розбиття |
| `<p><b>короткий текст</b></p>` без class, посеред глави | `pkSectionHeading` | Не впливає на розбиття — та сама глава триває |
| `<p><i>Видання, дата</i></p>` формату "Джерело, дата" | `pkSourceCitation` | Не впливає на розбиття |
| `<p><b><A NAME=PAGEn>[n]</A></b></p>` | `pkPageMarker` | Не створює окремий елемент у `Paragraphs` — постачає `StartPageNumber`/`PageBreakOffset` сусіднім параграфам і скидає лічильник `ParagraphOnPage` на 0 |
| `<p class="glink">` | — | **Відкидається повністю**, не створює `TParagraphContent` жодного типу |
| Попередній фрагмент не закінчується термінальною пунктуацією (`.!?»":`) АБО наступний починається з малої літери | — | Текстові фрагменти навколо `pkPageMarker` зливаються в один логічний абзац, `PageBreakOffset := Length(перший фрагмент)` — тобто точна позиція, де стояв маркер |
| Звичайний `<p>` без class, не підпадає під жодне правило вище | `pkText` | Не впливає на розбиття |

Семантика `TParagraphKind` (що означає кожен `Kind`) лишається в `Slovo_01`; тут — лише як його розпізнати в HTML. `PageBreakOffset` застосунок у MVP не рендерить (View 4, Частина F), але виробник його пише: зміна збереженого поля потребувала б переімпорту.

## 3. Обов'язки виробника перед тим, як віддати `library.db` (контракт формату — `Slovo_02`)

- **Та сама `sqlite3.dll`, що й у застосунку** (R6, B-31, D-08): амальгамація SQLite + `fts5-snowball` + `libstemmer_c` з українським стемером. Інша збірка дасть базу, стемовані таблиці якої застосунок не відкриє (`no such tokenizer`) або відкриє з іншими основами слів.
- `PRAGMA foreign_keys = ON` на час запису.
- **Стемовані таблиці** (R6): для кожної мови з `Modules.Language`, для якої Snowball має стемер, — view `Paragraphs_<lang>` / `Verses_<lang>` і FTS-таблиця `ParagraphsStem_<lang>` / `VersesStem_<lang>` за шаблоном `Slovo_02`. Мапа ISO 639-1 → алгоритм Snowball: `uk` → `ukrainian`, `ru` → `russian`, `en` → `english`. Мова без стемера — таблиці немає.
- Наприкінці: `INSERT INTO <t>(<t>) VALUES('rebuild')`, потім `'optimize'` — для `ParagraphsFTS`, `VersesFTS` і кожної `*Stem_<lang>`.
- `PRAGMA journal_mode = DELETE` (інакше `SQLITE_CANTOPEN` у `Program Files`), потім `VACUUM`. `page_size` — до наповнення.
- `Meta.SchemaVersion` = поточна версія формату (1); `Meta.BuiltAt` — час збірки.
- Усі модулі — і книги, і переклади Біблії — в одній базі; таблиці контенту несуть `ModuleId`.
- Усі текстові офсети — UTF-16 code units, від нуля, обчислені **після** нормалізації тексту.
- **`ModuleId` — глобально унікальний і незмінний** (B-30). На нього посилаються позиції читання в `data\settings.ini` і майбутні якорі анотацій (B-21). Перейменувати модуль між випусками бази не можна — це те саме, що змінити `ChapterOrder` наявної глави. Формат: без `=`, `,`, `:`; не починається з `;` або `[` (ключ INI, `Slovo_04` C.2).

## 4. Інваріанти, які перевіряє виробник (застосунок їм довіряє)

### Інваріанти серій (таблиця `Modules`; R3-08)

Один запит по таблиці `Modules` після наповнення. Правила: (1) `Series = ''` ⇒ `SeriesTitle = ''`, `SeriesOrder = 0`, `SortOrder = 0`; (2) `Series <> ''` ⇒ усі три непорожні/додатні; (3) усі модулі з однаковим `Series` мають однаковий `SeriesTitle` і `SeriesOrder`; (4) `SortOrder` унікальний у межах серії. Застосунок ці поля **читає й довіряє** — модуль, що порушує правило, лише стає не на своє місце в дереві. Лічильник глав/книг у `Modules` не зберігається (E-09) — нового інваріанту немає.

### Інваріанти Біблії (`Books`/`Verses`; R3-02)

`Books.ChapterCount` — денормалізоване поле; звірити його з фактом можна в кінці імпорту. Два запити нижче мають повернути **нуль рядків**:

```sql
-- (1) ChapterCount збігається з фактичною останньою главою книги
SELECT b.ModuleId, b.BookCode, b.ChapterCount, MAX(v.ChapterNumber) AS Actual
FROM Books b LEFT JOIN Verses v ON v.ModuleId = b.ModuleId AND v.BookCode = b.BookCode
GROUP BY b.ModuleId, b.BookCode
HAVING Actual IS NULL OR Actual <> b.ChapterCount;

-- (2) кожна глава 1..ChapterCount має принаймні один вірш (без "дірок")
WITH RECURSIVE seq(n) AS (SELECT 1 UNION ALL SELECT n + 1 FROM seq WHERE n < 200)
SELECT b.ModuleId, b.BookCode, seq.n AS MissingChapter
FROM Books b
JOIN seq ON seq.n <= b.ChapterCount
LEFT JOIN Verses v ON v.ModuleId = b.ModuleId AND v.BookCode = b.BookCode AND v.ChapterNumber = seq.n
WHERE v.Id IS NULL;
```

### Повнота стемованих індексів (R6, B-31)

Кожна мова модулів, для якої є стемер, має свою пару таблиць; кількість рядків у view мови дорівнює кількості рядків відповідної мови в `Paragraphs`/`Verses`; контрольне слово кожної мови знаходиться в стемованій таблиці у формі, відмінній від введеної (наприклад, `MATCH '"жертва"'` у `VersesStem_uk` повертає вірш зі словом «жертвою»).

### Межі офсетів (R3-07)

Для кожного рядка `Spans`: `StartOffset + Length ≤ довжина Text у UTF-16`; для `PageBreakOffset ≥ 0`: `PageBreakOffset < довжина Text у UTF-16`. SQLite довжину в UTF-16 не рахує — перевірка в Delphi.

## 5. Рішення цього проєкту (закрито 2026-11-01, R6)

Усі колишні відкриті питання IMP-1…IMP-6 вирішено; формулювання — рішення, ID лишаються для посилань.

**IMP-1 — нормалізація тексту: варіант A, мінімальна технічна.** NFC; видалити м'який перенос `#$00AD`, zero-width space `#$200B`, BOM; nbsp `#$00A0` → пробіл; згорнути повторні пробіли; `Trim` кожного абзацу. Лапки, тире й `ё` **не чіпаємо** — текст при читанні такий, як у виданні. Нормалізація — до обчислення будь-яких офсетів. (Відхилено: B — `ё→е` у тексті, спотворює читання; C — NFKC і уніфікація типографіки, пошуку нічого не дає.)

**IMP-2 — процес побудови.**
- **Метадані — таблиця-файл у репозиторії** `Import\books.csv` (UTF-8): один рядок на книгу — файл(и) CHM → `ModuleId`, `Category`, `Title`, `Author`, `Language`, `Series`, `SeriesTitle`, `SeriesOrder`, `SortOrder`, `Abbreviation`. Заповнюється вручну один раз; книга в CHM без рядка — помилка збірки, не мовчазний пропуск. Переклади Біблії — так само окремим файлом `bibles.csv` (+ абревіатури книг). Автоматичне витягування з CHM відхилено: серій там немає, а `ModuleId` міг би тихо змінитись з новою версією CHM (B-30).
- **Відтворюваність — детермінований порядок + текстовий дамп.** Книги обробляються в порядку `books.csv`, файли — у фіксованому порядку; поруч із `library.db` імпорт пише `dump\<ModuleId>.txt` (глави, абзаци з `Kind`, `StartPageNumber`, `PageBreakOffset`, `ParagraphOnPage`, текст). Дамп лежить у git; різницю між збірками показує звичайний diff. Байт-в-байт однаковий `.db` не вимагається (`BuiltAt`, внутрішня розкладка SQLite).
- Консольний проєкт у тому ж репозиторії, з логом; валідація — §4 і стемовані таблиці на контрольних словах.

**IMP-3 — корпус книг: усі книги CHM російською** (`Language = 'ru'`) → одна таблиця `ParagraphsStem_ru`. Переклади Біблії: uk, ru, en. Точна кількість модулів — за фактом імпорту; до того канонічна оцінка «≈42 книги + 3 переклади ≈ 45 модулів (оцінка, IMP-3)».

**IMP-4 — тести парсера: дамп + набір критичних фрагментів.** Дамп з IMP-2 ловить будь-яку зміну на всьому корпусі. Додатково 10–20 малих HTML-фрагментів із CHM — по одному на кожне правило таблиці §2 (злиття за термінальною пунктуацією, мала літера після маркера, `glava2`, епіграф, `pkSectionHeading`, `pkSourceCitation`, `glink`, абзац на межі сторінки з `PageBreakOffset`, лічильник `ParagraphOnPage`) — з очікуваним результатом у DUnitX; упалий тест називає правило. Стратегія тестування застосунку — `Slovo_03`, Частина C.

**IMP-5 — абревіатури: колонка зараз, UI потім.** `Modules.Abbreviation` і `Books.Abbreviation` (`TEXT NOT NULL DEFAULT ''`) — у форматі з першої збірки (`Slovo_02`), дані — з `books.csv`/`bibles.csv`, порожньо де невідомо. Застосунок у MVP їх не читає; цитати «PP 71.2» — post-MVP (E-13). Так формат не доведеться піднімати після релізу.

**IMP-6 — посилання під епіграфом: один блок** (E-10). Епіграф зберігається як є, разом із посиланням у дужках. Якщо колись захочеться окремого рядка — застосунок може відокремити останню дужку при показі, без зміни бази.
